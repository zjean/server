# Favorites: adopt upstream's backend, keep our v2 UI

**Date:** 2026-09-07
**Status:** EXECUTED, in the `sync/upstream-2026-09-07` branch (upstream 2.5.0). §3/§4 were
corrected during execution — see §10 for what the plan got wrong.
**Decision:** Delete the fork's favorites storage and HTTP surface. Adopt upstream's
`files_favorites` table and `/api/files/favorites` endpoints. Keep the entire `custom-v2`
favorites UI, re-pointed at upstream's contract. Keep a thin fork-owned bridge so NC
mobile favorites keep working.

Supersedes the storage and backend halves of
[`2026-06-10-favorites-custom-design.md`](2026-06-10-favorites-custom-design.md) and
[`2026-06-10-favorites-custom-implementation.md`](2026-06-10-favorites-custom-implementation.md).
Their merge-safety reasoning is now moot: upstream shipped the feature, so the conflict
surface those docs were avoiding is the surface we now want to sit on.

## 1. Why this is safe — the June table rename

`custom_files_favorites` was deliberately named to avoid a collision, and the comment in
`custom-favorites/schemas/files-favorites.schema.ts:10` says exactly why:

> Renamed from upstream-contrib's `files_favorites` to `custom_files_favorites` so there is
> never a table-name collision if upstream ships its own favorites.

Upstream's table is `files_favorites`. **The two tables coexist.** Upstream's migration
creates a new table and never touches ours, so merging upstream cannot destroy favorites
data. The data moves only when *our* migration copies it, and it is dropped only after.

**No favorites data is lost by this change**, provided §4 runs in the stated order.

## 2. What upstream shipped

`d3724ec5 feat(files): add file favorites across repositories`, plus
`a785d561 feat(favorites): show persisted file detail badges`. Built natively in `files`,
after our `upstream-contrib/favorites` PR was declined.

| | ours (`custom_files_favorites`) | upstream (`files_favorites`) |
|---|---|---|
| columns | userId, fileId, **path, spaceId, shareId**, createdAt | userId, fileId, createdAt |
| location model | access context stamped at favorite-time | re-derived per request from space/share membership |
| unreachable rows | stale stored path, shown as-is | resolved to `isDisabled: true` |
| list | `GET /api/custom-favorites` (`?limit`) → `navPath` | `GET /api/files/favorites` → `repository` + `path` + `name` + `displayRootName` + `isDisabled` |
| per-row star | second request: `GET /api/custom-favorites/ids` → `number[]` | `isFavorite` inside the browse response |
| add | `POST /api/custom-favorites/spaces/<path>` | `POST /api/files/favorites/<path>`, body `{ fileId }` → `{ fileId }` |
| remove | `DELETE /api/custom-favorites/spaces/<path>` | `DELETE /api/files/favorites`, body `{ fileId }` |

Dropping `path`/`spaceId`/`shareId` is a **functional gain**, not a loss: our stored paths
went stale when a file was moved or re-shared, while upstream re-resolves location on every
read and flags what it can no longer reach.

## 3. Migration journal — the first collision behind our fork-owned range

Upstream adds `0004_light_venom`. Our idx 4 is `0004_nc_sync_events`, and the fork owns
0004–0008. This is the first time upstream has added a migration *behind* our range, so it
has no precedent in this repo.

Two facts that make the fix safe:

- **`when` decides what is pending, not the filename.** Drizzle records the last applied
  migration's `created_at` in `__drizzle_migrations` and applies every journal entry with a
  later `when`. Upstream's `when` is `1787432793784`; our last (0008) is `1785241513665`.
  Renumbered to **0009**, it applies cleanly on existing deployments.
- **It cannot be skipped.** `0004_light_venom.sql` also carries an unrelated
  `users.externalId` column plus its unique index.

Also discard upstream's `meta/0004_snapshot.json` — it describes upstream's schema with none
of our custom tables. Our snapshot is regenerated by the tooling in §4.

## 4. The data-preserving migration (strict order)

**Ordering is the whole point.** `files_favorites` must exist before the copy, and
`custom_files_favorites` must survive until after it.

1. Merge upstream. Resolve `meta/_journal.json` by keeping our entries 0..8 and appending
   upstream's as **idx 9**, preserving its original `when` (`1787432793784`). Rename
   `backend/migrations/0004_light_venom.sql` → `0009_light_venom.sql`. Delete upstream's
   `meta/0004_snapshot.json`.
2. Remove `customFilesFavorites` from `backend/src/infrastructure/database/schema.ts` and
   delete the schema file (§5).
3. `npm run -w backend db:generate` — emits `0010_<name>.sql` (`DROP TABLE
   custom_files_favorites`) and, critically, a correct `meta/0010_snapshot.json`.
4. **Hand-insert the data copy above the drop** in the generated `0010` file:

   ```sql
   INSERT IGNORE INTO `files_favorites` (`userId`, `fileId`, `createdAt`)
     SELECT `userId`, `fileId`, `createdAt` FROM `custom_files_favorites`;
   --> statement-breakpoint
   DROP TABLE `custom_files_favorites`;
   ```

   `INSERT IGNORE` because both tables are keyed `(userId, fileId)`: a user who favorited
   the same file in both UIs after the sync would otherwise abort the migration. Both
   `userId` and `fileId` already carry the same FKs to `users.id` / `files.id`, so every
   copied row satisfies upstream's constraints. `DROP TABLE` removes our FKs with it.

**On editing a generated migration.** CLAUDE.md forbids hand-writing migration files, and
the stated reason is journal drift — `meta/_journal.json` falling out of sync so
`drizzle-kit migrate` silently skips a file. This plan keeps the journal and the snapshot
entirely tooling-generated and edits only the SQL body of a file the tooling already
registered. A schema diff cannot express a data copy, so there is no tooling-only path to a
non-destructive migration. This is a deliberate, narrow exception; note it in the PR body.

**Verify** on a database that has favorites rows, not an empty one:

```bash
npm run dev:db && npm run dev:migrate
# before: SELECT COUNT(*) FROM custom_files_favorites;
# after:  SELECT COUNT(*) FROM files_favorites;   -- must match
```

## 6. Why the bridge has to exist

Upstream's manager cannot serve `custom-mobile-compat`, for two independent reasons:

- **No `getFavoriteIds`.** `nc-propfind.service.ts:84` and `nc-sync-report.service.ts:121`
  need a cheap id Set to emit `oc:favorite` per row. Upstream's `getFavorites` runs three
  union queries across spaces, shares and external roots to resolve display locations — far
  too heavy for every directory listing. And the WebDAV path gets no free flag:
  upstream's `webdav-spaces.service.ts:158` calls `browse(req.user, space)` with no details
  argument, so `isFavorite` is never populated there.
- **Add/remove are id-addressed.** `nc-favorites-report.service.ts:130,133` handles a NC
  PROPPATCH, which carries only a path. Upstream's `addFavorite(user, space, fileId)`
  requires a client-supplied id.

**One upstream edit is required.** `files.module.ts:58` exports
`[FilesManager, FilesQueries, FilesLockManager, FilesQuotaManager, FilesMethods, FilesRecents]`
— neither favorites service is exported, so no other module can inject them. Add both to
that array as a single-line `mod(files): export favorites services` commit. It is the
lowest-conflict edit available (one array literal), it is greppable per CLAUDE.md's
`mod(<area>)` convention, and it must be re-applied on every sync — record it alongside the
`custom-recents-touch` re-apply note.

The alternative — reimplementing the location-resolving list query fork-side — means
duplicating ~244 lines of upstream union queries. Not worth it. Writes still route through
upstream's own `addFavorite` / `removeFavorite`, so there is one source of truth for
insert-upsert and delete semantics.

## 7. Frontend: keep every screen, re-point the seam

`FavoritesService` is the single boundary, which is what makes this cheap.

**`services/favorites.service.ts` — rewrite (71 lines)**

- Import `FileFavorite` / `FileFavoriteIdentity` from
  `files/schemas/file-favorite.interface` and `API_FILES_FAVORITES` from `files/constants/routes`.
- `loadFavorites()` drops its `limit` param — upstream's `GET` takes none. Our old default
  was 100 and the max 1000; upstream returns the lot. Favorites lists are small by nature,
  so accept it rather than paginating client-side.
- **Delete `loadFavoriteIds()` and the `favoriteIds` signal.** Per-row state comes from
  `isFavorite` on the browse response instead, which removes one HTTP request per directory
  (`file-browser.base.ts:470`).
- `toggle()` splits: `POST ${API_FILES_FAVORITES}/${encodeUrl(path)}` with body
  `{ fileId }`, and `DELETE` via `http.request('delete', API_FILES_FAVORITES, { body })` —
  Angular's `http.delete` cannot carry a body any other way.

**The negative-id trap.** Classic's ground truth,
`files/services/files.service.ts::toggleFavorite`, does:

```ts
if (file.id < 0) file.id = fileId
```

An unmaterialized file carries a **negative** id in the browse response; upstream's
`addFavorite` materializes the row and returns the real id in `{ fileId }`. Our current
`toggle()` ignores the response body entirely. It must adopt the returned id, or the row
keeps a negative id and the subsequent `DELETE` fails — `DeleteFileFavoriteDto` enforces
`@Min(1)`. This is precisely the sentinel-value class CLAUDE.md warns about.

**`screens/favorites/` — re-point (96 + 44 lines)**

Upstream's `FileFavorite` is `path` (repository-qualified **parent**) + `name`, which is the
same shape as `FileRecent`. The recents screen rebuilt in #453 already solves this:
`recents.component.ts:97` composes `` `${f.path}/${f.name}` ``. Mirror it — replace every
`fav.navPath` (lines 48, 52, 60, 72, 74, 77, 92, 94 and `favorites.component.html:20`) with
that composed path. `fileOriginFromPath` and `stripRepositoryPrefix` keep working unchanged.
Consider surfacing `isDisabled` as a dimmed, non-navigable row — upstream's own signal that
a favorite is no longer reachable. New capability; scope permitting.

**Call sites**

- `file-browser.component.html:177,303,420,422,488` — `favoritesService.isFavorite(f.id)`
  becomes `f.isFavorite`.
- `file-browser.base.ts:378` (context-menu label), `:470` (drop the id fetch), `:1009`
  (toggle, now sending `fileId` and adopting the response id).
- `inspector-panel.component.ts:284,292`.
- `screens/files/testing/file-browser-harness.ts:238,360` and
  `file-browser-contract.ts:911,1510` — the harness's `favoriteIds` Set gives way to
  `isFavorite` on fixture rows. These are the fork's only real frontend tests; keep them green.

`FileProps` gains `isFavorite?: boolean` upstream, so v2's file objects carry it for free
on `browseSpace` (which passes `withDetails = true`; note the gate is `favorites: !user.isLink`).

## 10. What execution corrected

### 10.1 The migration is fully tooling-generated (supersedes §3, §4 steps 1–3)

The plan said to carry upstream's `0004_light_venom.sql` renamed to `0009` and hand-write
`meta/0009_snapshot.json`. Don't. `drizzle-kit generate` produces both correctly, in two
passes, and the ambiguity that forces two passes is itself the reason:

**A single-pass generate asks an interactive question, and the wrong answer destroys data.**
With `files_favorites` added and `custom_files_favorites` removed in one diff, drizzle-kit
prompts "is this a RENAME?" (`promptNamedWithSchemasConflict`). Answering yes emits
`RENAME TABLE`, which keeps our three extra columns and silently makes the fork's table
*become* upstream's. In a non-TTY it just fails, which is the safe outcome; run it in a
terminal and the prompt is a live footgun.

So generate in two passes, neither of which is ambiguous:

1. Merge upstream, keep BOTH tables in `schema.ts`, `db:generate` → additions only. This
   emitted `0009_wise_night_thrasher.sql`, **byte-identical to upstream's own
   `0004_light_venom.sql`** — the check that the generated equivalent is faithful.
2. Remove `customFilesFavorites` from `schema.ts` and delete its schema file,
   `db:generate` → `0010_stormy_blink.sql`, containing only the `DROP TABLE`.
3. Hand-add the `INSERT IGNORE … SELECT` above that `DROP` (§4). Journal and both
   snapshots stay entirely tooling-written.

Upstream's migration file is not carried at all. The fork's chain has diverged from
upstream's since 0004 anyway, and generating is more reliable than hand-editing a snapshot.

### 10.3 The sync's real danger was not favorites at all

Upstream's `0148bfea` ("centralize file id validation and resolution") added
`assertValidFileId` to `getOrCreateUserFile` / `getOrCreateSpaceFile`:

```ts
if (!Number.isSafeInteger(fileId) || fileId === 0) throw 400
```

The fork passed **`0`** in six places to mean "no client-supplied id, take the path-keyed
branch". Every one of them now threw. `FileRowEnsurer` catches and returns 0 by design, so
**versioning silently stopped snapshotting entirely** — the build was clean, `npm run test`
was clean, and 84 e2e cases failed with "no versions were created".

The sentinel is now `NO_CLIENT_FILE_ID = -1`
(`custom-shared/constants/file-ids.ts`). Negative is upstream's own convention, not an
invention: `getProps()` sets `id: -stats.ino` for exactly this reason, and a negative still
fails the helpers' `fileId > 0` test, which is the branch we want.

Two things to carry forward from this:

- **A mocked-`FilesQueries` unit test can never catch it.** The guard added to
  `file-row-ensurer.service.spec.ts` imports the REAL `assertValidFileId` and asserts it
  accepts whatever the ensurer passes. Grep for `getOrCreate*File(0` and `id: 0` on every
  future sync.
- **The e2e suite is what found it, and it is advisory.** `npm run test` — the required
  check — was green over a dead feature. Run `npm -w backend run test:e2e` on any sync that
  touches `files/`.

### 10.5 The v2 UI kept a shared optimistic layer after all

§7 planned to read `isFavorite` straight off each row and drop the service's Set. Rows are
indeed authoritative now (the per-directory `GET /ids` request is gone), but the inspector
panel cannot reach the browser's rows, and both must agree on an in-flight toggle. So
`FavoritesService` keeps a small `overrides` map — `isFavorite(file)` is
`override ?? file.isFavorite` — cleared whenever a browse response lands.
